# Emotional Diary Service

Сервис, который помогает трейдеру бороться с эмоциями: обязательный допуск к сессии,
автоматические детекторы нарушений, блокировки с разбором и внешний контроль
через доверенное лицо.

Документы проекта (ТЗ, дизайн, архитектура, план разработки) лежат в Obsidian:
`Documents/Brain/Projects/Emotional Diary Service`.

## Стек

Python 3.12 + FastAPI · PostgreSQL 16 · SQLAlchemy 2 (async) · Alembic ·
модульный монолит со швами на разрез · события через outbox в базе.

## Запуск

Нужен только Docker Desktop.

```
copy .env.example .env      # Windows; на unix: cp .env.example .env
docker compose up -d --build
docker compose ps           # три строки со статусом Up
```

`-d` обязателен по практической причине: без него `docker compose up` держит
терминал и гасит весь стек, как только его закрыть или прервать. Сервис после
этого выглядит как «localhost refused to connect», хотя всё было настроено верно.

Дальше:

- <http://localhost:5173> — интерфейс (вход, настройки)
- <http://localhost:8000> — страница состояния сервиса
- <http://localhost:8000/docs> — документация API

Логи: `docker compose logs -f api` или `docker compose logs -f web`.
Помни, что `logs` показывает и остановленные контейнеры, а `ps` — только живые:
если `logs` что-то пишет, а `ps` пуст, значит стек уже погас.

Остановить: `docker compose down`.
Стереть базу и начать с нуля: `docker compose down -v`.
Пересобрать после правок зависимостей: `docker compose up -d --build`.

### Ключ шифрования: нужен, чтобы подключить источник

Ключи источников (TMM, дальше Binance) хранятся в базе зашифрованными, поэтому
без мастер-ключа подключить источник нельзя — сервис ответит
`secret_key_missing`. Сгенерировать и вписать в `.env` один раз:

```
docker compose run --rm --no-deps api python -m eds.entrypoints.genkey
```

Полученную строку положить в `EDS_SECRET_KEY` в `.env` и перезапустить стек.
На странице состояния появится `secret_key_set: true`.

**Менять мастер-ключ нельзя.** После смены уже сохранённые ключи источников
не расшифруются: сервис скажет об этом прямо, но подключать источники придётся
заново.

## Что уже работает

**Шаг 4 — настоящий TMM (первая часть).** Адаптер TMM API v2: ключ в заголовке
`API-KEY`, три адреса с переключением на зеркало при сбое, чтение лимитов из
заголовков `x-ratelimit-*` с притормаживанием и обработкой `429`. Подключение
ключом на экране настроек: ключ проверяется до создания подключения, хранится
зашифрованным и наружу не возвращается никогда. Сразу после подключения видна
проба — счета, словарь тегов входа и последние сделки за 30 дней в том виде,
как их понял сервис; в базу проба ничего не пишет, потому что истории мы
не импортируем. Сверка забирает сделки тем же путём, что и фейковый источник.
Журнал сверок и снимок лимитов видны на карточке источника. Переключение между
источниками требует подтверждения со списком последствий.

Чего в этой части ещё нет: SSE-потока от TMM (сделки приезжают по кнопке
«Сверить сейчас», а не сами) и расписания сверок. Это вторая часть шага 4.

**Шаг 3 — разметка и нарушения.** Полный экран разметки: словарь тегов
с отметкой «это нарушение», покрытие разметкой, коэффициент дисциплины и цена
эмоций за период. Своя разметка сделок для источников без тегов — кнопками
в ленте, с немедленным пересчётом метрик. Порог достоверности: до 30 торговых
дней выводы помечаются «мало данных».

**Шаг 2 — источник и лента сделок.** Порт `TradeSource` и фейковый источник:
сделки подаются в него кнопкой и забираются обычной сверкой — тем же путём,
которым пойдут настоящие. Приём считает торговый день по времени открытия
и таймзоне трейдера, значимость по порогу, разметку по тегам; повторная сверка
ничего не дублирует. Лента сделок с фильтрами и итогами по всей выборке,
кривая дня, словарь тегов с отметкой «это нарушение» — её изменение
переразмечает принятые сделки через событийную шину.

**Шаг 1 — вход и настройки.** Регистрация и вход по куки-сессии (`HttpOnly`
плюс CSRF-токен двойной отправкой), модуль `identity`, экран настроек:
таймзона, граница торгового дня, пороги чека, порог значимости, режим наблюдения.
Список активных входов с возможностью оборвать любой. Фронт — React 18 + TypeScript
+ Vite + TanStack Query, тёмная тема из прототипа.

**Шаг 0 — каркас.** Страница состояния показывает версию, соединение с базой,
номер применённой миграции, девять схем модулей и состояние событийной шины.
Кнопка «Отправить тестовое событие» публикует событие в `events.outbox`;
консьюмер забирает его и сдвигает курсор — это видно на той же странице.

План следующих шагов — в документе «План разработки».

## Тесты

Без базы (границы модулей, контракты, адаптер TMM на подменённых ответах):

```
docker compose run --rm api pytest -q
```

С базой (шина, схемы, сквозной путь подключения и сверки):

```
docker compose run --rm -e TEST_DATABASE_URL=postgresql+asyncpg://eds:eds_local_password@db:5432/eds api pytest -q
```

Настоящий ключ TMM тестам не нужен: провайдер подменяется через `respx`,
всё остальное в тестах настоящее — база, сессии, шифрование, приём сделок.

## Структура

```
src/eds/
├── contracts/     события и порты — единственное, что импортируют все
├── app/           оркестрация: единственное место, знающее несколько модулей
├── platform/      конфиг, база, шина, логи, аутентификация, шифрование
├── modules/       модули: у каждого свой пакет и своя схема в базе
│   └── source/adapters/  fake, tmm (дальше binance)
├── entrypoints/   процессы: api, genkey (дальше — stream, worker, bot)
└── web/           страница состояния сервиса
web/               SPA: React + TypeScript + Vite
alembic/           миграции, одна история на все схемы
tests/             включая проверку границ между модулями
```

## Правила, о которых легко забыть

- `.env` в репозиторий не попадает. В нём живёт только мастер-ключ шифрования;
  ключи источников трейдер вводит в интерфейсе, и они лежат в базе зашифрованными.
- В клиенте TMM нет методов записи, и это осознанно: режим ключа через API
  не проверить, поэтому единственная настоящая гарантия — отсутствие таких
  методов в коде (ТЗ 4.1, Архитектура 4.8).
- Модуль не импортирует другой модуль. Это проверяет `tests/test_boundaries.py`.
- Откат миграций не поддерживается: назад — только восстановлением дампа.
- Все расчёты на сервере. Фронт ничего не считает сам.
