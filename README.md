# Emotional Diary Service

Сервис, который помогает трейдеру бороться с эмоциями: обязательный допуск к сессии,
автоматические детекторы нарушений, блокировки с разбором и внешний контроль
через доверенное лицо.

Документы проекта (ТЗ, дизайн, архитектура, план разработки) лежат в Obsidian:
`Documents/Brain/Projects/Emotional Diary Service`.

## Стек

Python 3.12 + FastAPI · PostgreSQL 16 · SQLAlchemy 2 (async) · Alembic ·
модульный монолит со швами на разрез · события через outbox в базе.

## Запуск

Нужен только Docker Desktop.

```
copy .env.example .env      # Windows; на unix: cp .env.example .env
docker compose up -d --build
docker compose ps           # три строки со статусом Up
```

`-d` обязателен по практической причине: без него `docker compose up` держит
терминал и гасит весь стек, как только его закрыть или прервать. Сервис после
этого выглядит как «localhost refused to connect», хотя всё было настроено верно.

Дальше:

- <http://localhost:5173> — интерфейс (вход, настройки)
- <http://localhost:8000> — страница состояния сервиса
- <http://localhost:8000/docs> — документация API

Логи: `docker compose logs -f api` или `docker compose logs -f web`.
Помни, что `logs` показывает и остановленные контейнеры, а `ps` — только живые:
если `logs` что-то пишет, а `ps` пуст, значит стек уже погас.

Остановить: `docker compose down`.
Стереть базу и начать с нуля: `docker compose down -v`.
Пересобрать после правок зависимостей: `docker compose up -d --build`.

### Ключ шифрования: нужен, чтобы подключить источник

Ключи источников (TMM, дальше Binance) хранятся в базе зашифрованными, поэтому
без мастер-ключа подключить источник нельзя — сервис ответит
`secret_key_missing`. Сгенерировать и вписать в `.env` один раз:

```
docker compose run --rm --no-deps api python -m eds.entrypoints.genkey
```

Полученную строку положить в `EDS_SECRET_KEY` в `.env` и перезапустить стек.
На странице состояния появится `secret_key_set: true`.

**Менять мастер-ключ нельзя.** После смены уже сохранённые ключи источников
не расшифруются: сервис скажет об этом прямо, но подключать источники придётся
заново.

## Что уже работает

**Шаг 8 — правила: конструктор.** Экран «Правила» собран по прототипу
`RuleBuilder.dc.html`: слева список системных триггеров и своих правил, справа
конструктор «Если — То», под ним «Правило словами».

Словарь условий — три показателя из ТЗ 6.3: убыточных сделок подряд, просадка
от пика дня, убыток суммарно. Он зависит от активного источника: просадка
с учётом открытых позиций и нереализованный убыток появятся только с Binance,
а до тех пор стоят в списке затенёнными с причиной. Вырезать их молча было бы
хуже — трейдер, читавший про честную просадку, искал бы её и не нашёл.

Условия складываются плоским списком со связками «и» / «или», не больше пяти.
ТЗ 6.3 говорило «не ограничено», Архитектура ч.2 §3.6 — «не больше пяти»;
решением от 23.09 считаем, что ч.2 уточнила ТЗ.

**Фразу считает сервер**, и черновую тоже — через `POST /rules/preview`. Это
не перестраховка: та же строка уйдёт в Telegram и ляжет в запись инцидента
как текст правила на момент срабатывания. Собранная ещё и на фронте, она
однажды разойдётся, и «почему меня заблокировало» перестанет объясняться само.

Системные триггеры SR-1…SR-4 создаются сами при первом открытии экрана — по
требованию, а не при регистрации, чтобы они появились и у тех, кто завёл
аккаунт раньше. Отключить их нельзя, и это ограничение базы, а не проверка
в коде: триггер на `rules.rules` роняет `UPDATE`, который пытается их погасить.
Настраивается у них только то, что перечислено в `editable_fields` — длительность
блокировки, условия снятия, сигнал другу; условия не настраиваются, потому что
тремя показателями они не выражаются и живут в коде обработчика.

Удаление правила не стирает строку: на правило будут ссылаться инциденты,
и история «почему меня заблокировало» должна читаться и после того, как правило
убрали. Правка поднимает `version` по той же причине.

Отступления от прототипа, все вынужденные: название правила — поле ввода,
а не заголовок (иначе новое правило не назвать); чип «включено» кликается
и у своих правил есть «Удалить» (иначе выключение и удаление остались бы
только в API); у системного триггера блок «Если» — текст, а не селекты;
карточек системных правил четыре, а в прототипе три — ТЗ 6.5 описывает
SR-1…SR-4, и спрятать четвёртый значило бы спрятать триггер, который будет
срабатывать; доверенное лицо названо «доверенным лицом», а не «Максимом».

Чего в этом шаге нет: **правила не срабатывают**. Нет движка, счётчиков дня,
инцидентов и блокировок — это шаги 9 и 10. Счётчик срабатываний показывает
честный ноль у всех правил, а не правдоподобное число из прототипа, и экран
прямо говорит, что движок появится на шаге 9. Алерт в Telegram хранится как
настройка и никуда не уходит (шаг 13). Сигнал доверенному лицу и снятие по его
подтверждению выключены: без подтверждённого контакта ТЗ 6.8 их не разрешает.

**Шаг 7 — стрики.** День засчитывается только при выполнении всех пяти условий
ТЗ 7.1: пройден чек, заполнены запись дня и разбор, ноль нарушений, ноль
нарушенных блокировок, ноль сделок без допуска. Правило зачёта — чистая функция
от фактов дня: модуль стриков не читает чужие схемы, факты собирает оркестрация
и передаёт контрактом. Поэтому все сочетания условий проверяются таблицей,
а не прогоном сценария.

Причина незачёта хранится вместе с отметкой и оттуда же показывается: «есть
нарушения», «разбор не заполнен», «были сделки без допуска», «запись дня не
заполнена». Одно место расчёта означает, что показанная причина не может
разойтись с настоящей.

Выходные и отпуск серию не рвут. День без сделок, чека и записи вообще не
попадает в расчёт — он не удлиняет серию и не обрывает её. Заморозка делает то
же самое с днём намеренно: две в месяц, к дню с нарушением не применяется,
прошлое заморозить нельзя — иначе заморозка стала бы способом переписать
историю задним числом.

Рядом с текущей серией показываются лучший результат и дней без нарушений
в этом месяце (ТЗ 7.2): серия обрывается одним днём, а месяц — нет, и после
срыва видно, что месяц не потерян. Формулировки нейтральные: «В тишине
и дисциплине», без пристыживания.

Одно отступление от прототипа: кнопки заморозки в нём нет ни на одном экране.
Она добавлена в карточку «Дисциплина» и на экран закрытой сессии — замораживают
день, в который не торгуют, а в такой день до карточки открытой сессии трейдер
не доходит. Повторное нажатие по уже замороженному дню ничего не стоит.

Чего в этом шаге нет: сброса стрика правилом и системными триггерами (шаги 9
и 10), ретропересчёта после позднего тега (шаг 11). Нарушенные блокировки
в расчёт зачёта уже заложены, но появиться им пока негде — блокировок нет.

**Шаг 6 — дневник и пост-сессионный разбор.** Экраны собраны по прототипу:
в дневнике календарь — постоянная левая колонка на всех уровнях, а переключатель
меняет только правую панель. Календарь не декорация, а способ навигации: клик
по клетке выбирает день, неделю или месяц, и на каждом уровне видно, где
находишься. Записи на трёх уровнях: день, неделя, месяц. Оценка, статус, ментальные теги и текст; пресеты статусов
и тегов сервис предлагает, но не ограничивает ими — статус и теги свободный
текст, а справочник превратил бы «допиши своё» в правку схемы. Запись правится
48 часов от конца периода, дальше остаётся комментарий: запись должна остаться
тем, что трейдер думал тогда, а не тем, что он думает об этом сейчас.

Рядом с каждой записью — факты периода, которые считает сервер: сделки,
нарушения, результат, допуск дня, а для недели и месяца метрики из ТЗ 5.1 —
коэффициент дисциплины, покрытие разметкой, цена эмоций, отдельно «слито
на эмоциях» и отдельно «нарушений в плюс», дней без допуска. Три суммы вместо
одной со знаком: сальдо прячет и убыток, и прибыльное нарушение, а прибыльное
нарушение опаснее убыточного.

Пост-сессионный разбор: соблюдал план, что дёрнуло, оценка исполнения (не
результата), один вывод. Разбор возможен только по закрытому дню, один раз.
Закрытие сессии ставит разбор в очередь, и **пока он не заполнен, новый чек
не выдаётся** — перекрытие на весь экран с одной кнопкой. Жёсткость
сознательная: разбор входит в условия стрика и в условие следующей сессии.

Чего в этом шаге нет: блокировок и compliance (шаг 9) — на их местах плашки
и нули, а не прочерки.

**Шаг 5 — торговый день и пре-маркет чек.** Сессии не существует, пока не пройден
чек готовности: пять вопросов из ТЗ, шкала 1–5, максимум 25 баллов. У вопроса про
желание отыграться переворачиваются подписи шкалы, а не арифметика: «1 — сильное
желание», «5 — нет желания». Единая шкала «больше — лучше» держится подписями,
поэтому одно и то же число значит одно и то же на экране, в базе и в правилах. Три исхода по порогам из настроек трейдера: зелёный открывает
сессию, красный открывает её с напоминанием урезать размер (напоминание, а не
механика — сервис ничего не отправляет на биржу), «нет допуска» не открывает
её вовсе. Перепройти чек в тот же день нельзя, и запрет стоит ограничением базы,
а не проверкой в коде.

Экран «Сегодня» собирается одним запросом `GET /today`: состояние дня, допуск,
счётчики дня (результат, просадка от пика, серия убытков, суммарный убыток),
кривая дня, последние сделки и список того, что требует внимания. Счётчики
считает сервер, таймеры идут от его времени. Сессию можно закрыть раньше границы
дня, а день, который уже кончился, закрывается сам при первом чтении.

Чего в этом шаге нет: пост-сессионного разбора (шаг 6), стрика (шаг 7),
блокировок и «ближе всего к срабатыванию» (шаг 9). Запрет «не разобрал вчера —
нет допуска сегодня» написан и проверен тестом, но выставлять состояние
«разбор не закрыт» сервис начнёт на шаге 6 — вместе с формой, которой его можно
закрыть.

**Шаг 4 — настоящий TMM (первая часть).** Адаптер TMM API v2: ключ в заголовке
`API-KEY`, три адреса с переключением на зеркало при сбое, чтение лимитов из
заголовков `x-ratelimit-*` с притормаживанием и обработкой `429`. Подключение
ключом на экране настроек: ключ проверяется до создания подключения, хранится
зашифрованным и наружу не возвращается никогда. Сразу после подключения видна
проба — счета, словарь тегов входа и последние сделки за 30 дней в том виде,
как их понял сервис; в базу проба ничего не пишет, потому что истории мы
не импортируем. Сверка забирает сделки тем же путём, что и фейковый источник.
Журнал сверок и снимок лимитов видны на карточке источника. Переключение между
источниками требует подтверждения со списком последствий.

Чего в этой части ещё нет: SSE-потока от TMM (сделки приезжают по кнопке
«Сверить сейчас», а не сами) и расписания сверок. Это вторая часть шага 4.

**Шаг 3 — разметка и нарушения.** Полный экран разметки: словарь тегов
с отметкой «это нарушение», покрытие разметкой, коэффициент дисциплины и цена
эмоций за период. Своя разметка сделок для источников без тегов — кнопками
в ленте, с немедленным пересчётом метрик. Порог достоверности: до 30 торговых
дней выводы помечаются «мало данных».

**Шаг 2 — источник и лента сделок.** Порт `TradeSource` и фейковый источник:
сделки подаются в него кнопкой и забираются обычной сверкой — тем же путём,
которым пойдут настоящие. Приём считает торговый день по времени открытия
и таймзоне трейдера, значимость по порогу, разметку по тегам; повторная сверка
ничего не дублирует. Лента сделок с фильтрами и итогами по всей выборке,
кривая дня, словарь тегов с отметкой «это нарушение» — её изменение
переразмечает принятые сделки через событийную шину.

**Шаг 1 — вход и настройки.** Регистрация и вход по куки-сессии (`HttpOnly`
плюс CSRF-токен двойной отправкой), модуль `identity`, экран настроек:
таймзона, граница торгового дня, пороги чека, порог значимости, режим наблюдения.
Список активных входов с возможностью оборвать любой. Фронт — React 18 + TypeScript
+ Vite + TanStack Query, тёмная тема из прототипа.

**Шаг 0 — каркас.** Страница состояния показывает версию, соединение с базой,
номер применённой миграции, девять схем модулей и состояние событийной шины.
Кнопка «Отправить тестовое событие» публикует событие в `events.outbox`;
консьюмер забирает его и сдвигает курсор — это видно на той же странице.

План следующих шагов — в документе «План разработки».

## Тесты

Без базы (границы модулей, контракты, адаптер TMM на подменённых ответах):

```
docker compose run --rm api pytest -q
```

С базой (шина, схемы, сквозной путь подключения и сверки):

```
docker compose run --rm -e TEST_DATABASE_URL=postgresql+asyncpg://eds:eds_local_password@db:5432/eds api pytest -q
```

Настоящий ключ TMM тестам не нужен: провайдер подменяется через `respx`,
всё остальное в тестах настоящее — база, сессии, шифрование, приём сделок.

## Структура

```
src/eds/
├── contracts/     события, порты и правило торгового дня — общее для всех
├── app/           оркестрация: единственное место, знающее несколько модулей
├── platform/      конфиг, база, шина, логи, аутентификация, шифрование
├── modules/       модули: у каждого свой пакет и своя схема в базе
│   └── source/adapters/  fake, tmm (дальше binance)
├── entrypoints/   процессы: api, genkey (дальше — stream, worker, bot)
└── web/           страница состояния сервиса
web/               SPA: React + TypeScript + Vite
alembic/           миграции, одна история на все схемы
tests/             включая проверку границ между модулями
```

## Правила, о которых легко забыть

- `.env` в репозиторий не попадает. В нём живёт только мастер-ключ шифрования;
  ключи источников трейдер вводит в интерфейсе, и они лежат в базе зашифрованными.
- В клиенте TMM нет методов записи, и это осознанно: режим ключа через API
  не проверить, поэтому единственная настоящая гарантия — отсутствие таких
  методов в коде (ТЗ 4.1, Архитектура 4.8).
- Модуль не импортирует другой модуль. Это проверяет `tests/test_boundaries.py`.
- Откат миграций не поддерживается: назад — только восстановлением дампа.
- Все расчёты на сервере. Фронт ничего не считает сам.
